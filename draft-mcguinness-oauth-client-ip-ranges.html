OAuth Client IP Range Metadata

Abstract

This specification defines OAuth client metadata parameters for declaring the IP address ranges from which a client originates network requests. The client_ip_ranges parameter carries a set of IPv4 and IPv6 prefixes by value. The client_ip_ranges_uri parameter references an HTTPS resource containing the set, which supports large and frequently changing sets through standard HTTP retrieval and caching. The parameters can be used with OAuth 2.0 Dynamic Client Registration, OAuth Client ID Metadata Documents, and other mechanisms that convey client metadata. Authorization servers and other parties that obtain a client's metadata can use the declared ranges as an input to network access control.¶

1. Introduction

OAuth clients that run as hosted services commonly originate requests from a known set of network addresses. Authorization servers, resource servers, and the network infrastructure in front of them use these addresses to restrict which sources can reach the token endpoint and protected resources. In current practice, client operators publish their address ranges through vendor-specific mechanisms, and deployments transcribe them into network access controls by hand. Client metadata (Section 2 of [RFC7591]) has no parameter for the network origins of a client.¶

This specification defines two client metadata parameters that declare the IP address ranges from which a client originates requests: client_ip_ranges, which carries the ranges by value, and client_ip_ranges_uri, which references a Client IP Range Document that contains them. As with the jwks and jwks_uri parameters of [RFC7591], the two forms have the same semantics and are mutually exclusive. The reference form lets a client publish a large or frequently changing set without updating its registration. The parameters can be used with OAuth 2.0 Dynamic Client Registration [RFC7591], OAuth Client ID Metadata Documents [CIMD], and other mechanisms that convey client metadata.¶

Declared ranges are an input to network access control. Deployments use source address restrictions to limit where a client's credentials and grants can be used. Declared ranges do not authenticate the client or authorize a request (Section 5).¶

This specification defines the metadata and the processing requirements for authorization servers that use it. Other parties that obtain a client's metadata can apply the same processing. Selecting the clients subject to enforcement, approving declared ranges, and configuring network enforcement points are local policy; Section 6.1 describes typical deployments. Enforcement by resource servers is outside the scope of this specification.¶

1.1. Requirements Notation and Conventions

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [BCP14] (RFC2119) (RFC8174) when, and only when, they appear in all capitals, as shown here.¶

1.2. Terminology

This specification uses the terms "access token", "authorization server", "client", "client authentication", "protected resource", "redirection endpoint", "resource owner", "resource server", and "token endpoint" defined by OAuth 2.0 [RFC6749], and the terms "client metadata" and "software statement" defined by OAuth 2.0 Dynamic Client Registration [RFC7591].¶

This specification defines the following terms:¶

IP range set:

The set of IPv4 and IPv6 prefixes that a client declares, either by value with client_ip_ranges or by reference with client_ip_ranges_uri.¶

Client IP Range Document:

A JSON document, defined in Section 3, that contains an IP range set and is referenced by client_ip_ranges_uri.¶

accepted IP range set:

The IP range set, if any, that an authorization server has validated and accepted for a client and currently uses for it, including such a set after narrowing (Section 7.2). An authorization server that stops using an IP range set no longer has an accepted IP range set for the client.¶

2. Client IP Range Metadata

This specification defines the following client metadata parameters (Section 2 of [RFC7591]) for declaring the IP address ranges from which a client originates requests (Section 5):¶

client_ip_ranges:

OPTIONAL. JSON array of strings, each an IPv4 or IPv6 prefix (Section 2.1). The array is a set. The authorization server MUST NOT assign meaning to the order of entries or to duplicate entries. An empty array declares an empty IP range set.¶

client_ip_ranges_uri:

OPTIONAL. URL of a Client IP Range Document (Section 3) that contains the client's IP range set. The URL MUST use the https scheme and MUST NOT contain a fragment or userinfo component [RFC3986]. The authorization server retrieves the document as described in Section 4.¶

client_ip_ranges_uri conveys an IP range set by reference, with the same semantics as client_ip_ranges. The client_ip_ranges and client_ip_ranges_uri parameters MUST NOT both be present in the same client metadata. If neither is present, the client makes no declaration, which differs from declaring an empty IP range set. This specification sets no maximum number of entries; the authorization server applies its own bounds (Section 7.4).¶

2.1. Prefix Syntax

Each prefix MUST conform to the ip-prefix type defined in Section 4 of [RFC9911], that is, match in full every pattern of either the ipv4-prefix or the ipv6-prefix type. A value that does not conform to the ip-prefix type is invalid.¶

The client, and the party hosting a Client IP Range Document, MUST represent each prefix in the canonical format of that type, with all bits outside the prefix length set to zero and, for IPv6, the address represented as defined in Section 4 of [RFC5952]. A value that is not in canonical format is nonetheless valid and denotes the prefix given by its network address and prefix length (Section 4 of [RFC9911]). For example, 192.0.2.1/24 denotes 192.0.2.0/24, and 2001:DB8::1/64 denotes 2001:db8::/64.¶

A prefix within the IPv4-mapped IPv6 address range ::ffff:0:0/96 (Section 2.5.5.2 of [RFC4291]) is invalid; IPv4 ranges are expressed as IPv4 prefixes. Every prefix length that the ip-prefix type permits, including zero, is valid. Whether to accept a broad prefix is local policy (Section 7.2).¶

2.2. Metadata Validation

If a trusted software statement (Section 2.3 of [RFC7591]) carries client_ip_ranges or client_ip_ranges_uri, the authorization server ignores both parameters elsewhere in the client metadata, whether in a registration request or in a Client ID Metadata Document (Section 4.3 of [CIMD]). This extends the precedence rule of Section 2 of [RFC7591] to the pair of parameters.¶

After this precedence is applied, client IP range metadata is invalid if any of the following is true:¶

  1. Both client_ip_ranges and client_ip_ranges_uri are present.¶

  2. The value of client_ip_ranges is not an array of strings, or any entry is an invalid prefix (Section 2.1).¶

  3. The value of client_ip_ranges_uri does not meet the requirements for client_ip_ranges_uri in Section 2.¶

  4. The value of client_ip_ranges has more entries than the authorization server's bound on prefixes (Section 7.4).¶

If a client registration request contains invalid client IP range metadata, the authorization server responds with an HTTP 400 (Bad Request) error response as described in Section 3.2.2 of [RFC7591], using invalid_client_metadata as the error code value, or invalid_software_statement if the invalid value comes from a trusted software statement. If a Client ID Metadata Document [CIMD] contains invalid client IP range metadata, the authorization server treats the client IP range metadata as a validation failure (Section 4.5) and does not treat the rest of the document as invalid.¶

An authorization server that does not support these parameters ignores them (Section 2 of [RFC7591]). The client information response (Section 3.2.1 of [RFC7591]) shows whether the authorization server registered them.¶

3. Client IP Range Document

A Client IP Range Document is a JSON [RFC8259] object with the following member:¶

client_ip_ranges:

REQUIRED. JSON array of prefixes, with the same syntax and semantics as client_ip_ranges (Section 2).¶

The authorization server MUST ignore members that it does not understand. A document whose top-level object contains duplicate member names is invalid; Section 4 of [RFC8259] notes that receivers handle such objects unpredictably. The document is self-contained, and the authorization server MUST NOT retrieve other resources to complete it.¶

All prefixes in the document apply equally to each client whose metadata references it. Multiple clients can reference the same document, and the document can be hosted by a party other than the client, such as its hosting provider.¶

The following is a non-normative example of a Client IP Range Document:¶

{
  "client_ip_ranges": [
    "192.0.2.0/24",
    "198.51.100.10/32",
    "2001:db8:100::/48",
    "2001:db8:200::/48"
  ]
}
¶

4. Retrieval and Acceptance

4.1. Retrieval

An authorization server retrieves a Client IP Range Document by sending an HTTP GET request to the client_ip_ranges_uri URL, subject to Section 7.3. A response is successful if it has status code 200 (OK), the application/json media type, and a complete body within the authorization server's bounds (Section 7.4), or if it has status code 304 (Not Modified) (Section 15.4.5 of [RFC9110]) in answer to a conditional request (Section 6.2). A 304 response indicates that the stored response is current.¶

The party hosting a Client IP Range Document MUST serve it with the application/json media type and MUST NOT require authentication to retrieve it unless that party and the authorization server have agreed on an authentication mechanism, which is outside the scope of this specification. The authorization server MUST NOT send credentials associated with an OAuth request, such as client credentials, access tokens, or authorization codes, when retrieving a Client IP Range Document.¶

The authorization server MUST NOT treat a failed retrieval, an unsuccessful response, or an invalid document as an empty IP range set; each is a failure (Section 4.5).¶

4.2. Caching

The party hosting a Client IP Range Document SHOULD support HTTP caching [RFC9111] and SHOULD include the Cache-Control (Section 5.2 of [RFC9111]) and ETag (Section 8.8.3 of [RFC9110]) response header fields.¶

The accepted IP range set is application state, distinct from any HTTP cache (Section 6 of [RFC9111]). A fresh response does not make its IP range set accepted, and expiry of a cached response does not end use of the accepted IP range set (Section 4.3). The authorization server SHOULD retrieve the document periodically to obtain changes.¶

4.3. Acceptance

Before accepting an IP range set, whether it is conveyed by client_ip_ranges or in a Client IP Range Document, the authorization server MUST ensure the following:¶

  1. The client IP range metadata that conveys the set is valid (Section 2.2), and every prefix in the set is valid (Section 2.1).¶

  2. If the set was obtained from a Client IP Range Document, the response is successful (Section 4.1) and the complete document is valid (Section 3).¶

If any of these checks fails, the authorization server MUST reject the entire set. Acceptance is also subject to local policy (Section 7.2). Registering client IP range metadata does not by itself accept its IP range set.¶

An accepted IP range set replaces the previously accepted IP range set in full; this specification defines no incremental update format. The accepted IP range set remains in effect until the authorization server accepts a replacement, narrows it, or stops using it (Section 7.2). A validated IP range set that has not yet been accepted under local policy does not replace it.¶

A client SHOULD add a prefix to its IP range set before it originates requests from addresses in that prefix and SHOULD keep the prefix in the set until it no longer originates requests from them.¶

4.4. Changes to Client Metadata

A client's metadata can change the value of client_ip_ranges_uri, switch between client_ip_ranges and client_ip_ranges_uri, or remove both. The new metadata replaces the previous declaration.¶

When the metadata changes representation or URI, the accepted IP range set remains in effect until the authorization server accepts a set under the new metadata or stops using it (Section 4.3). An invalid new declaration or an unretrievable new document is a failure (Section 4.5). If the previous metadata contained client_ip_ranges_uri, the authorization server does not retrieve that URI again for the client.¶

Removal of both parameters withdraws the client's declaration (Section 4.5). In a client update request (Section 2.2 of [RFC7592]), omitting both parameters requests their removal, which the authorization server can ignore. The client information response (Section 3 of [RFC7592]) shows whether they were removed.¶

4.5. Failures and Withdrawal

An authorization server MUST NOT admit a source address that it did not admit before because of a failure to retrieve a Client IP Range Document, a failure to validate client IP range metadata or a retrieved document, or, by itself, withdrawal of the client's declaration (Section 4.4).¶

After a failure, the authorization server MAY continue to use the accepted IP range set, within the retention limit (Section 7.2). Relaxing enforcement after a withdrawal is a local policy decision, not an automatic consequence of the withdrawal.¶

If an authorization server requires an accepted IP range set for a client, it MUST reject requests from the client while it has no accepted IP range set for the client, whether because the client has made no declaration, because its declaration is invalid or cannot be retrieved, or because a validated IP range set has not yet been accepted under local policy.¶

Otherwise, what applies while a client has no accepted IP range set is local policy, except after the retention limit (Section 7.2) is exceeded.¶

4.6. Lifecycle Summary

The following table summarizes the accepted IP range set after each event, as specified in Section 4.3, Section 4.5, and Section 7.2. It adds no requirements. Whenever a client has no accepted IP range set, an authorization server that requires one rejects requests from the client.¶

Table 1
Event Accepted IP range set afterward
First declaration validated None, until accepted under local policy
Replacement accepted The replacement
Replacement validated, not yet accepted Unchanged or narrowed to the intersection, at most until the retention limit
Retrieval or validation fails Unchanged, at most until the retention limit
Declaration withdrawn Unchanged, at most until the retention limit
Retention limit exceeded None; an authorization server that was enforcing the set rejects requests from the client until it accepts a new set or local policy removes the client from enforcement

5. Use of Client IP Range Metadata

The IP range set identifies source addresses from which the client originates requests directly to authorization servers and resource servers, such as token requests and requests to protected resources. It does not describe the network origins of user agents, redirection endpoints, or requests initiated by the resource owner.¶

A source address matches an IP range set if it is within any of its prefixes. Before matching, the authorization server MUST convert an IPv4-mapped IPv6 source address to the IPv4 address it contains. An authorization server that enforces a client's accepted IP range set admits requests from the client only from source addresses that match it; if that set is empty, it admits none.¶

An authorization server MAY use the IP range set as an input to local network access control. The IP range set is a declaration made by or on behalf of the client, and a match does not authenticate the client or authorize a request. The authorization server MUST NOT use a source address match in place of client authentication, access token validation, or any other security control required by OAuth.¶

Enforcement by resource servers, including how a resource server determines the client associated with a request and obtains that client's metadata, is outside the scope of this specification and could be addressed by a companion specification.¶

5.1. Enforcement by Authorization Servers

An authorization server can enforce a client's accepted IP range set at the token endpoint and at other endpoints that receive direct requests from the client, once it has identified the client, either through client authentication or, for a public client (Section 2.1 of [RFC6749]), as the client to which a grant presented in the request was issued. This specification does not define how an authorization server identifies a public client in a request that presents no grant, such as a device authorization request (Section 3.1 of [RFC8628]).¶

In a response to a party that has not authenticated as the client, an authorization server SHOULD NOT indicate that a request was rejected because of its source address. This specification does not yet define an error response for such a rejection (Appendix C).¶

6. Implementation Considerations

6.1. Enforcement Points

Enforcing the IP range set of a specific client requires knowing which client sent a request. A network enforcement point that operates below HTTP, such as a firewall, observes the source address but not the client, so it can enforce only the aggregate of the IP range sets of the clients permitted to reach an endpoint. An authorization server can enforce each client's IP range set once it has identified the client (Section 5.1).¶

For example, an enterprise administrator approves a hosted client for use with the enterprise's authorization server and reviews the IP range set in its metadata. The enterprise adds the approved ranges to the network allowlist in front of its token endpoint, and the authorization server rejects token requests from that client that originate outside them. When the client's IP range set later changes, local policy determines whether the change is applied automatically, such as an addition within an approved scope, or is held for administrator approval (Section 7.2).¶

When an authorization server enforces a client's accepted IP range set, requests from source addresses outside that set are rejected until the authorization server accepts a replacement that includes them. Deployments that require an accepted IP range set need an administrative path to restore access, such as approving a replacement set. Enforcing a client's IP range set at the client configuration endpoint (Section 2 of [RFC7592]) can prevent the client from correcting a declaration made by value.¶

6.2. Retrieval Scheduling

This specification does not require retrieval during the processing of an OAuth request; an authorization server can retrieve documents in the background. An authorization server typically schedules the next retrieval when the stored response's freshness lifetime (Section 4.2 of [RFC9111]) ends, within local minimum and maximum intervals. A client needs to allow for these intervals, and for approval delays, when adding a prefix (Section 4.3).¶

To revalidate, an authorization server sends a conditional GET request carrying the If-None-Match header field (Section 13.1.2 of [RFC9110]) with the entity tag of the most recent complete response it stored from that URI (Section 4.3 of [RFC9111]). That response can be newer than the one from which the accepted IP range set was derived. Without a stored complete response, the authorization server sends an unconditional request.¶

6.3. Document Size

Section 8.7 of [CIMD] recommends that authorization servers read at most 5 kilobytes of a Client ID Metadata Document. A client whose IP range set does not fit within such a limit can use client_ip_ranges_uri. An authorization server sets its bounds on Client IP Range Documents (Section 7.4) independently of bounds on client metadata, because such documents are expected to be larger. The gzip content coding (Section 8.4.1.3 of [RFC9110]) can reduce the transfer size of large documents.¶

7. Security Considerations

The security considerations of the mechanism that conveys the client metadata, such as Section 5 of [RFC7591] or Section 8 of [CIMD], also apply.¶

7.1. Trust in Declared Ranges

Client IP range metadata is a declaration made by or on behalf of the client. Inclusion of a prefix does not establish that the client exclusively owns or controls the addresses it contains. Prefixes of shared infrastructure, such as cloud provider or carrier-grade NAT egress ranges, also carry traffic from other parties.¶

Whether to use declared ranges in network access control is a local trust decision. A software statement (Section 2.3 of [RFC7591]) vouches only for the values it contains: for client_ip_ranges, the prefixes; for client_ip_ranges_uri, the URL but not the referenced document. The party hosting the document asserts its contents, and accepting them automatically is a separate decision to trust that party within an approved scope (Section 7.2). An authorization server can require that client_ip_ranges_uri share an origin with the client identifier URL of a Client ID Metadata Document [CIMD].¶

7.2. Changes to Declared Ranges

A change to a client's IP range set can broaden or narrow the source addresses admitted by a network policy derived from it. An authorization server MUST NOT treat the addition of a prefix to a client's IP range set as granting network access by itself. When local policy permits automatic updates for the client and the change falls within an approved scope, such as prefixes contained in supernets that the authorization server has configured for the client, the authorization server MAY accept the change automatically. Detecting unexpected expansion of a client's IP range set, including the addition of overly broad prefixes, helps an authorization server decide which changes to hold for approval. The authorization server SHOULD apply changes atomically, so that no intermediate state admits a source address that neither the previous nor the new IP range set contains.¶

Continued use of an accepted IP range set that may no longer match the client's current declaration admits addresses that may have been reassigned to another party. An authorization server SHOULD set a retention limit on how long it continues to use an accepted IP range set while retrieval or validation of the client's current declaration fails, after the client withdraws its declaration, and while a validated replacement has not been accepted under local policy.¶

Before accepting a validated replacement, an authorization server MAY narrow the accepted IP range set to its intersection with the replacement, so that it admits only source addresses that both sets match. The narrowed set remains the accepted IP range set; the replacement is still not accepted.¶

When the retention limit is exceeded, the authorization server stops using the set and has no accepted IP range set for the client. An authorization server that was enforcing the set rejects requests from the client until it accepts a new IP range set or an explicit local policy decision removes the client from enforcement.¶

7.3. Server-Side Request Forgery

Retrieval of client_ip_ranges_uri causes an authorization server to send a request to a URL supplied in client metadata, which creates a risk of Server-Side Request Forgery (SSRF) attacks. When retrieving a Client IP Range Document, the following requirements apply:¶

  1. The authorization server MUST NOT retrieve a URL that does not meet the requirements for client_ip_ranges_uri in Section 2.¶

  2. The authorization server MUST verify the server certificate as described in Section 4.3.4 of [RFC9110] and MUST NOT accept a document retrieved over a connection that fails this verification. This strengthens the requirement of that section for automated clients.¶

  3. The authorization server MUST NOT automatically follow HTTP redirects (Section 15.4 of [RFC9110]).¶

  4. The authorization server MUST NOT connect to an address that the IANA special-purpose address registries ([RFC6890], [RFC8190]) list as not globally reachable, unless local policy explicitly permits that destination. This check applies to the address of each connection after DNS resolution. An authorization server that retrieves through a configured forward proxy relies on the proxy to apply this check.¶

An authorization server retrieving a URL obtained from a Client ID Metadata Document is also subject to Section 8.6 of [CIMD].¶

7.4. Resource Exhaustion

A malicious or compromised party hosting a Client IP Range Document can return an oversized document, a highly compressed response, or a large number of overlapping prefixes. An authorization server MUST bound retrieval time, response size, decompressed size, and the number of prefixes in an IP range set, whether conveyed by value or in a document. If a document exceeds any bound, the authorization server MUST reject the entire document. This specification sets no minimum value for any of these bounds.¶

7.5. Source Address Interpretation

Proxies, load balancers, and network address translation change the source address that an authorization server observes. The authorization server MUST determine the source address from a trusted source of connection-origin information. It MUST NOT use a forwarding header field, such as Forwarded [RFC7239] or X-Forwarded-For, as the source address unless it was set by an intermediary the authorization server trusts. Because a trusted intermediary can append its own observation to a field that already carries entries supplied by an attacker (Section 8.1 of [RFC7239]), the authorization server MUST select the source address from such a field using its configuration of trusted proxies and MUST NOT trust an entry merely because a trusted intermediary forwarded or appended to the field.¶

8. Privacy Considerations

Client IP range metadata describes network infrastructure rather than end users. However, when a client runs on infrastructure associated with an individual, such as a residential network, its declared ranges can reveal that individual's network location. A publicly retrievable Client IP Range Document discloses the client's egress infrastructure to any party.¶

Retrieval of client_ip_ranges_uri reveals to the party hosting the document the addresses and retrieval timing of authorization servers that evaluate the client, which can indicate the authorization servers and resource servers with which the client is used (see also Section 9.1 of [CIMD]).¶

Appendix A. Examples

A.1. Dynamic Client Registration by Value

The following is a non-normative example of a client registration request (Section 3.1 of [RFC7591]) that declares an IP range set by value:¶

POST /register HTTP/1.1
Host: server.example.com
Content-Type: application/json

{
  "client_name": "Example Client",
  "grant_types": ["client_credentials"],
  "token_endpoint_auth_method": "private_key_jwt",
  "jwks_uri": "https://client.example.com/jwks.json",
  "client_ip_ranges": [
    "192.0.2.0/24",
    "2001:db8:100::/48"
  ]
}
¶

A.2. Client ID Metadata Document by Reference

The following is a non-normative example of a Client ID Metadata Document [CIMD] that declares an IP range set by reference:¶

{
  "client_id": "https://client.example.com/oauth/client.json",
  "client_name": "Example Client",
  "redirect_uris": ["https://client.example.com/callback"],
  "token_endpoint_auth_method": "private_key_jwt",
  "jwks_uri": "https://client.example.com/jwks.json",
  "client_ip_ranges_uri": "https://client.example.com/ip-ranges.json"
}
¶

A.3. Document Retrieval

The following is a non-normative example of a request for the Client IP Range Document referenced above:¶

GET /ip-ranges.json HTTP/1.1
Host: client.example.com
Accept: application/json
Accept-Encoding: gzip
¶

The following is a non-normative example of a successful response:¶

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: public, max-age=3600
ETag: "ranges-v42"

{
  "client_ip_ranges": [
    "192.0.2.0/24",
    "198.51.100.0/24",
    "2001:db8:100::/48"
  ]
}
¶

The following non-normative example shows a later conditional request and a response indicating that the document is unchanged:¶

GET /ip-ranges.json HTTP/1.1
Host: client.example.com
Accept: application/json
If-None-Match: "ranges-v42"
¶ 
HTTP/1.1 304 Not Modified
Cache-Control: public, max-age=3600
ETag: "ranges-v42"

Appendix B. Related Work

[JAFAR] defines a format for publishing the IP address ranges of automated HTTP clients. Its prefixes are objects with separate IPv4 and IPv6 members and optional service identifiers, the document carries a creation time, and a prefix object that has both or neither address member is ignored. This specification instead uses one prefix array for both client_ip_ranges and the Client IP Range Document, so that both forms share one syntax and one validation procedure; rejects the whole set when any prefix is invalid (Section 4.3), so that a document is applied completely or not at all; and relies on client metadata to associate the set with a client, so that the document needs no service identifiers.¶

Clients can announce planned changes to their IP range sets through a separately specified notification mechanism, such as event types delivered using the Shared Signals Framework [SSF]. This specification does not define advance announcement events or scheduled activation of ranges.¶
