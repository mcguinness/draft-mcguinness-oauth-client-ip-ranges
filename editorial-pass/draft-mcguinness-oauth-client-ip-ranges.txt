                     OAuth Client IP Range Metadata
             draft-mcguinness-oauth-client-ip-ranges-latest

Abstract

   This specification defines OAuth client metadata parameters for
   declaring the IP address ranges from which a client originates
   network requests.  The client_ip_ranges parameter carries a set of
   IPv4 and IPv6 prefixes by value.  The client_ip_ranges_uri parameter
   references an HTTPS resource containing the set, which supports large
   and frequently changing sets through standard HTTP retrieval and
   caching.  The parameters can be used with OAuth 2.0 Dynamic Client
   Registration, OAuth Client ID Metadata Documents, and other
   mechanisms that convey client metadata.  Authorization servers and
   other parties that obtain a client's metadata can use the declared
   ranges as an input to network access control.

1.  Introduction

   OAuth clients that run as hosted services commonly originate requests
   from a known set of network addresses.  Authorization servers,
   resource servers, and the network infrastructure in front of them use
   these addresses to restrict which sources can reach the token
   endpoint and protected resources.  In current practice, client
   operators publish their address ranges through vendor-specific
   mechanisms, and deployments transcribe them into network access
   controls by hand.  Client metadata (Section 2 of [RFC7591]) has no
   parameter for the network origins of a client.

   This specification defines two client metadata parameters that
   declare the IP address ranges from which a client originates
   requests:

   *  client_ip_ranges carries the ranges by value.

   *  client_ip_ranges_uri references a Client IP Range Document that
      contains them.

   As with the jwks and jwks_uri parameters of [RFC7591], the two forms
   have the same semantics and are mutually exclusive.  The reference
   form lets a client publish a large or frequently changing set without
   updating its registration.  The parameters can be used with OAuth 2.0
   Dynamic Client Registration [RFC7591], OAuth Client ID Metadata
   Documents [CIMD], and other mechanisms that convey client metadata.

   Declared ranges are an input to network access control.  They do not
   authenticate the client or authorize a request (Section 5).  Firewall
   policy, network access authorization decisions, and the configuration
   of network enforcement points are outside the scope of this
   specification; Section 6 describes how deployments use the metadata.

1.1.  Requirements Notation and Conventions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in
   [BCP14] (RFC2119) (RFC8174) when, and only when, they appear in all
   capitals, as shown here.

1.2.  Terminology

   This specification uses the terms "access token", "authorization
   server", "client", "client authentication", "protected resource",
   "redirection endpoint", "resource owner", "resource server", and
   "token endpoint" defined by OAuth 2.0 [RFC6749], and the terms
   "client metadata" and "software statement" defined by OAuth 2.0
   Dynamic Client Registration [RFC7591].

   This specification defines the following terms:

   IP range set:  The set of IPv4 and IPv6 prefixes that a client
      declares, either by value with client_ip_ranges or by reference
      with client_ip_ranges_uri.

   Client IP Range Document:  A JSON document, defined in Section 3,
      that contains an IP range set and is referenced by
      client_ip_ranges_uri.

   accepted IP range set:  The IP range set, if any, that a consumer has
      validated and accepted for a client and currently uses for it.  A
      consumer that stops using an IP range set no longer has an
      accepted IP range set for the client.

   publisher:  An entity that publishes a client's IP range set, either
      by value in client metadata or in a Client IP Range Document.  The
      publisher of a Client IP Range Document can differ from the entity
      that provides the client metadata referencing it.

   consumer:  An entity that processes client IP range metadata, such as
      an authorization server or a resource server.

2.  Client IP Range Metadata

   The following client metadata parameters convey a client's IP range
   set, by value or by reference.

2.1.  client_ip_ranges

   OPTIONAL.  JSON array of strings, each an IPv4 or IPv6 prefix
   (Section 2.3) identifying source addresses from which the client
   originates requests (Section 5).

   The array is a set.  Consumers MUST NOT assign meaning to the order
   of entries or to duplicate entries.  This specification does not
   limit the number of entries.

   An empty array declares an empty IP range set.  Absence of both
   client_ip_ranges and client_ip_ranges_uri means the client makes no
   declaration; it does not imply an empty IP range set.

2.2.  client_ip_ranges_uri

   OPTIONAL.  URL of a Client IP Range Document (Section 3), whose IP
   range set has the same semantics as a client_ip_ranges value.  The
   URL MUST use the https scheme and MUST NOT contain a fragment or
   userinfo component [RFC3986].  Consumers retrieve the document as
   described in Section 4.

   The client_ip_ranges and client_ip_ranges_uri parameters MUST NOT
   both be present in the same client metadata.

2.3.  Prefix Syntax

   Each prefix MUST conform to the ip-prefix type defined in Section 4
   of [RFC9911].  A value that does not conform to the ip-prefix type is
   invalid.  In addition:

   *  Publishers MUST use the canonical format of that type: all bits
      outside the prefix length set to zero and, for IPv6, the address
      represented as defined in Section 4 of [RFC5952].

   *  Consumers MUST interpret each prefix by its network address and
      prefix length, not by its textual form.  Consumers MUST NOT treat
      a value as invalid solely because it is not in canonical format.
      For example, a consumer interprets 192.0.2.1/24 as 192.0.2.0/24
      and 2001:DB8::1/64 as 2001:db8::/64.

   *  A prefix within the IPv4-mapped IPv6 address range ::ffff:0:0/96
      (Section 2.5.5.2 of [RFC4291]) is invalid.  IPv4 ranges are
      expressed as IPv4 prefixes.

   *  Every prefix length that the ip-prefix type permits, including
      zero, is valid.  Whether to accept a broad prefix is local policy
      (Section 7.2).

2.4.  Metadata Validation

   If a trusted software statement (Section 2.3 of [RFC7591]) carries
   client_ip_ranges or client_ip_ranges_uri, the authorization server
   ignores both parameters elsewhere in the client metadata, whether in
   a registration request or in a Client ID Metadata Document
   (Section 4.3 of [CIMD]).  This extends the precedence rule of
   Section 2 of [RFC7591] to the pair of parameters.

   After this precedence is applied, client IP range metadata is invalid
   if any of the following is true:

   1.  Both client_ip_ranges and client_ip_ranges_uri are present.

   2.  The value of client_ip_ranges is not an array of strings, or any
       entry is an invalid prefix (Section 2.3).

   3.  The value of client_ip_ranges_uri does not meet the requirements
       of Section 2.2.

   An authorization server handles invalid client IP range metadata as
   follows:

   *  In a dynamic client registration request, the authorization server
      responds with HTTP status code 400 and the invalid_client_metadata
      error code (Section 3.2.2 of [RFC7591]).

   *  In a Client ID Metadata Document [CIMD], the authorization server
      handles the metadata as a validation failure (Section 4.5) and
      does not treat the rest of the document as invalid.

   An authorization server that does not support these parameters
   ignores them (Section 2 of [RFC7591]).  The client information
   response (Section 3.2.1 of [RFC7591]) shows whether the authorization
   server registered them.

3.  Client IP Range Document

   A Client IP Range Document is a JSON [RFC8259] object with the
   following member:

   client_ip_ranges:  REQUIRED.  JSON array of prefixes, with the syntax
      and semantics defined in Section 2.1.

   The following rules apply to the document:

   *  The document MUST be served with the application/json media type.

   *  Consumers MUST ignore members they do not understand.

   *  A document whose top-level object contains duplicate member names
      is invalid (Section 4 of [RFC8259]).

   *  The document is self-contained.  Consumers MUST NOT retrieve other
      resources to complete it.

   All prefixes in the document apply equally to each client whose
   metadata references it.  Multiple clients can reference the same
   document.

   The following is an example of a Client IP Range Document:

   {
     "client_ip_ranges": [
       "192.0.2.0/24",
       "198.51.100.10/32",
       "2001:db8:100::/48",
       "2001:db8:200::/48"
     ]
   }

4.  Retrieval and Acceptance

4.1.  Retrieval

   A consumer retrieves a Client IP Range Document by sending an HTTP
   GET request to the client_ip_ranges_uri URL, subject to Section 7.3.
   A successful response has status code 200 (OK) and contains the
   complete document.  In response to a conditional request
   (Section 4.2), a 304 (Not Modified) response (Section 15.4.5 of
   [RFC9110]) is also successful and indicates that the retained
   response is current.

   Publishers MUST NOT require authentication to retrieve a Client IP
   Range Document unless the publisher and consumer have agreed on an
   authentication mechanism, which is outside the scope of this
   specification.  Consumers MUST NOT send credentials associated with
   an OAuth request, such as client credentials, access tokens, or
   authorization codes, when retrieving a Client IP Range Document.

   A failed retrieval, a malformed response, or a document that is
   incomplete or exceeds the consumer's bounds (Section 7.4) MUST NOT be
   treated as an empty IP range set; it is a failure (Section 4.5).

4.2.  Caching

   Publishers SHOULD support HTTP caching [RFC9111] and SHOULD include
   the Cache-Control (Section 5.2 of [RFC9111]) and ETag (Section 8.8.3
   of [RFC9110]) response header fields.

   Consumers SHOULD revalidate the document with a conditional GET
   request carrying the If-None-Match header field (Section 13.1.2 of
   [RFC9110]) and the entity tag of the most recent complete response
   from that URI that the consumer has retained (Section 4.3 of
   [RFC9111]).  That response can hold an IP range set that awaits
   approval; it need not be the one from which the accepted IP range set
   was obtained.  A consumer that has retained no complete response
   sends an unconditional request.

   The accepted IP range set is application state, distinct from any
   HTTP cache (Section 6 of [RFC9111]):

   *  A fresh response does not make its IP range set accepted.

   *  Expiry of a cached response does not end use of the accepted IP
      range set (Section 4.3).

   Consumers SHOULD retrieve the document periodically to obtain
   changes.

4.3.  Acceptance

   A consumer MUST validate an IP range set completely, including every
   prefix, before accepting it, whether the set is conveyed by
   client_ip_ranges or in a Client IP Range Document, and MUST reject
   the entire set if any part of it is invalid.  Acceptance is also
   subject to local policy (Section 7.2).

   An accepted IP range set replaces the previously accepted IP range
   set in full; this specification defines no incremental update format.
   The accepted IP range set remains in effect until the consumer
   accepts a replacement or stops using it (Section 7.2).  A validated
   IP range set that awaits approval does not replace it.

   Publishers SHOULD publish a new prefix before the client originates
   requests from it and SHOULD continue to publish a prefix until the
   client no longer originates requests from it.

4.4.  Changes to Client Metadata

   A client's metadata can change the value of client_ip_ranges_uri,
   switch between client_ip_ranges and client_ip_ranges_uri, or remove
   both.  The new metadata replaces the previous declaration.

   When the metadata changes representation or URI:

   *  The accepted IP range set remains in effect until the consumer
      accepts a set under the new metadata or stops using it
      (Section 4.3).  An invalid new declaration or an unretrievable new
      document is a failure (Section 4.5).

   *  If the previous metadata contained client_ip_ranges_uri, the
      consumer does not retrieve that URI again for the client or reuse
      its cached responses or validators (Section 2 of [RFC9111]).

   Removal of both parameters withdraws the client's declaration
   (Section 4.5).  In a client update request (Section 2.2 of
   [RFC7592]), omitting both parameters requests their removal, which
   the authorization server can ignore.  The client information response
   (Section 3 of [RFC7592]) shows whether they were removed.

4.5.  Failures and Withdrawal

   The following MUST NOT cause a consumer to admit a source address
   that it did not admit before:

   *  a failure to retrieve a Client IP Range Document;

   *  a failure to validate client IP range metadata or a retrieved
      document; and

   *  withdrawal of the client's declaration (Section 4.4), by itself.

   After a failure, the consumer MAY continue to use the accepted IP
   range set, within the limit described in Section 7.2.  Whether to
   relax enforcement after a withdrawal is local policy.

   A consumer can require an accepted IP range set for a client.  Such a
   consumer MUST reject requests from the client while it has no
   accepted IP range set for the client, whether because:

   *  the client has made no declaration;

   *  its declaration is invalid or cannot be retrieved; or

   *  a validated IP range set awaits approval.

   For other consumers, what applies while a client has no accepted IP
   range set is local policy.

5.  Use of Client IP Range Metadata

   The IP range set identifies source addresses from which the client
   originates requests directly to authorization servers and resource
   servers, such as token requests and requests to protected resources.
   It does not describe the network origins of user agents, redirection
   endpoints, or requests initiated by the resource owner.

   A source address matches an IP range set if it is within any of its
   prefixes.  Before matching, consumers MUST convert an IPv4-mapped
   IPv6 source address to the IPv4 address it contains.  A consumer that
   enforces a client's accepted IP range set admits requests from the
   client only from source addresses that match it; if that set is
   empty, it admits none.

   Consumers MAY use the IP range set as an input to local network
   access control.  The IP range set is a declaration by its publisher,
   and a match does not authenticate the client or authorize a request.
   Consumers MUST NOT use a source address match in place of client
   authentication, access token validation, or any other security
   control required by OAuth.

   Enforcement by resource servers, including how a resource server
   determines the client associated with a request and obtains that
   client's metadata, is outside the scope of this specification and
   could be addressed by a companion specification.

5.1.  Enforcement by Authorization Servers

   An authorization server can enforce a client's accepted IP range set
   at the token endpoint and at other endpoints that receive direct
   requests from the client.  Enforcement requires identifying the
   client:

   *  through client authentication; or

   *  for a public client (Section 2.1 of [RFC6749]), through the client
      to which the grant presented in the request was issued.

   An authorization server SHOULD NOT indicate, in a response to a party
   that has not authenticated as the client, that a request was rejected
   because of its source address.  This specification does not yet
   define an error response for such a rejection (Appendix B).

6.  Implementation Considerations

6.1.  Enforcement Points

   Enforcing the IP range set of a specific client requires knowing
   which client sent a request:

   *  A network enforcement point that operates below HTTP, such as a
      firewall, observes the source address but not the client.  It can
      enforce only the aggregate of the IP range sets of the clients
      permitted to reach an endpoint.

   *  An authorization server can enforce each client's IP range set
      once it has identified the client (Section 5.1).

   For example, an enterprise administrator approves a hosted client for
   use with the enterprise's authorization server and reviews the IP
   range set in its metadata.  The enterprise adds the approved ranges
   to the network allowlist in front of its token endpoint, and the
   authorization server rejects token requests from that client that
   originate outside them.  When the publisher later changes the set,
   local policy determines whether the change is applied automatically,
   such as an addition within an approved scope, or is held for
   administrator approval (Section 7.2).

6.2.  Retrieval Scheduling

   This specification does not require retrieval during the processing
   of an OAuth request; consumers can retrieve documents in the
   background.  Consumers choose retrieval intervals within local
   minimum and maximum values.  Publishers allow for these intervals,
   and for approval delays, when publishing a new prefix (Section 4.3).

6.3.  Document Size

   Section 8.7 of [CIMD] recommends that authorization servers read at
   most 5 kilobytes of a Client ID Metadata Document.  A client whose IP
   range set does not fit within such a limit uses client_ip_ranges_uri.
   Consumers set their bounds on Client IP Range Documents (Section 7.4)
   independently of bounds on client metadata, because such documents
   are expected to be larger.  Publishers and consumers can use the gzip
   content coding (Section 8.4.1.3 of [RFC9110]) to reduce the transfer
   size of large documents.

7.  Security Considerations

   The security considerations of the mechanism that conveys the client
   metadata, such as Section 5 of [RFC7591] or Section 8 of [CIMD], also
   apply.

7.1.  Trust in Declared Ranges

   Client IP range metadata is a declaration by its publisher.
   Inclusion of a prefix does not establish that the client exclusively
   owns or controls the addresses it contains.  Prefixes of shared
   infrastructure, such as cloud provider or carrier-grade NAT egress
   ranges, also carry traffic from other parties.

   Whether to use declared ranges in network access control is a local
   trust decision.  A software statement (Section 2.3 of [RFC7591])
   vouches only for the values it contains:

   *  For client_ip_ranges, it vouches for the prefixes.

   *  For client_ip_ranges_uri, it vouches for the URL, not the
      referenced document.  The document's publisher asserts its
      contents, and accepting them automatically is a separate decision
      to trust that publisher within an approved scope (Section 7.2).

   A consumer can require that client_ip_ranges_uri share an origin with
   the client identifier URL of a Client ID Metadata Document [CIMD].

7.2.  Changes to Declared Ranges

   A change to a published IP range set can broaden or narrow the source
   addresses admitted by a network policy derived from it.  When
   processing such changes:

   *  Consumers MUST NOT treat publication of a new prefix as granting
      network access by itself.

   *  Consumers MAY accept updates automatically when local policy
      authorizes the publisher and the change falls within an approved
      scope, such as prefixes contained in supernets that the consumer
      has configured for the client.

   *  Consumers SHOULD detect unexpected expansion of a declared IP
      range set, including the addition of overly broad IPv4 or IPv6
      prefixes.

   *  Consumers SHOULD apply changes atomically, so that no intermediate
      state admits a source address that neither the previous nor the
      new IP range set contains.

   Continued use of an accepted IP range set after the publisher has
   removed a prefix admits addresses that may have been reassigned to
   another party.  Consumers SHOULD limit how long they continue to use
   an accepted IP range set while retrieval or validation of the
   client's current declaration fails.  When the limit is exceeded, the
   consumer stops using the set and has no accepted IP range set for the
   client.  Because of Section 4.5, stopping can narrow, but not widen,
   the source addresses admitted for the client.

7.3.  Server-Side Request Forgery

   Retrieval of client_ip_ranges_uri causes a consumer to send a request
   to a URL supplied in client metadata, which is a server-side request
   forgery vector.  When retrieving a Client IP Range Document,
   consumers:

   1.  MUST NOT retrieve a URL that does not meet the requirements of
       Section 2.2.

   2.  MUST verify the server certificate as described in Section 4.3.4
       of [RFC9110].

   3.  MUST NOT automatically follow HTTP redirects (Section 15.4 of
       [RFC9110]).

   4.  MUST NOT connect to an address that the IANA special-purpose
       address registries [RFC6890] list as not globally reachable,
       unless local policy explicitly permits that destination.  This
       check applies to the address of each connection after DNS
       resolution.  A consumer that retrieves through a configured
       forward proxy relies on the proxy to apply this check.

   An authorization server retrieving a URL obtained from a Client ID
   Metadata Document is also subject to Section 8.6 of [CIMD].

7.4.  Resource Exhaustion

   A malicious or compromised publisher can return an oversized
   document, a highly compressed response, or a large number of
   overlapping prefixes.  Consumers MUST bound retrieval time, response
   size, decompressed size, and prefix count.  If a document exceeds any
   bound, the consumer MUST reject the entire document.  This
   specification sets no minimum value for any of these bounds.

7.5.  Source Address Interpretation

   Proxies, load balancers, and network address translation change the
   source address that a consumer observes.  Consumers MUST determine
   the source address from a trusted source of connection-origin
   information.  For forwarding header fields, such as Forwarded
   [RFC7239] or X-Forwarded-For:

   *  Consumers MUST NOT use such a field as the source address unless
      it was set by an intermediary the consumer trusts.

   *  A trusted intermediary can append its own observation to a field
      that already carries entries supplied by an attacker (Section 8.1
      of [RFC7239]).  Consumers MUST select the source address from such
      a field using their configuration of trusted proxies, and MUST NOT
      trust an entry merely because a trusted intermediary forwarded or
      appended to the field.

8.  Privacy Considerations

   Client IP range metadata describes network infrastructure rather than
   end users, but it can still disclose information:

   *  When a client runs on infrastructure associated with an
      individual, such as a residential network, its declared ranges can
      reveal that individual's network location.

   *  A publicly retrievable Client IP Range Document discloses the
      client's egress infrastructure to any party.

   *  Retrieval of client_ip_ranges_uri reveals to the publisher the
      addresses and retrieval timing of consumers that evaluate the
      client, which can indicate the authorization servers and resource
      servers with which the client is used (see also Section 9.1 of
      [CIMD]).

9.  IANA Considerations

   This specification requests registration of the following client
   metadata in the "OAuth Dynamic Client Registration Metadata" registry
   established by [RFC7591].

   *  Client Metadata Name: client_ip_ranges
   *  Client Metadata Description: Array of IPv4 and IPv6 prefixes from
      which the client originates requests
   *  Change Controller: IETF
   *  Specification Document(s): Section 2.1 of this specification

   *  Client Metadata Name: client_ip_ranges_uri
   *  Client Metadata Description: HTTPS URL of a document containing
      the IPv4 and IPv6 prefixes from which the client originates
      requests
   *  Change Controller: IETF
   *  Specification Document(s): Section 2.2 of this specification

10.  Examples

10.1.  Dynamic Client Registration by Value

   The following is an example of a client registration request
   (Section 3.1 of [RFC7591]) that declares an IP range set by value:

   POST /register HTTP/1.1
   Host: server.example.com
   Content-Type: application/json

   {
     "client_name": "Example Client",
     "grant_types": ["client_credentials"],
     "token_endpoint_auth_method": "private_key_jwt",
     "jwks_uri": "https://client.example.com/jwks.json",
     "client_ip_ranges": [
       "192.0.2.0/24",
       "2001:db8:100::/48"
     ]
   }

10.2.  Client ID Metadata Document by Reference

   The following is an example of a Client ID Metadata Document [CIMD]
   that declares an IP range set by reference:

   {
     "client_id": "https://client.example.com/oauth/client.json",
     "client_name": "Example Client",
     "token_endpoint_auth_method": "private_key_jwt",
     "jwks_uri": "https://client.example.com/jwks.json",
     "client_ip_ranges_uri": "https://client.example.com/ip-ranges.json"
   }

10.3.  Document Retrieval

   The following is an example of a request for the Client IP Range
   Document referenced above:

   GET /ip-ranges.json HTTP/1.1
   Host: client.example.com
   Accept: application/json
   Accept-Encoding: gzip

   The following is an example of a successful response:

   HTTP/1.1 200 OK
   Content-Type: application/json
   Cache-Control: public, max-age=3600
   ETag: "ranges-v42"

   {
     "client_ip_ranges": [
       "192.0.2.0/24",
       "198.51.100.0/24",
       "2001:db8:100::/48"
     ]
   }

   The following example shows a later conditional request and a
   response indicating that the document is unchanged:

   GET /ip-ranges.json HTTP/1.1
   Host: client.example.com
   Accept: application/json
   If-None-Match: "ranges-v42"

   HTTP/1.1 304 Not Modified
   Cache-Control: public, max-age=3600
   ETag: "ranges-v42"

Appendix A.  Related Work

   [JAFAR] defines a format for publishing the IP address ranges of
   automated HTTP clients, with optional per-prefix service identifiers
   and a document creation time.  A Client IP Range Document carries
   only prefixes, because client metadata associates it with the client.

   Publishers can announce planned changes to their IP range sets
   through a separately specified notification mechanism, such as event
   types delivered using the Shared Signals Framework [SSF].  This
   specification does not define advance announcement events or
   scheduled activation of ranges.
